# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

IT Job Radar is a Chrome extension (Manifest V3) that periodically pulls job listings from Djinni and DOU RSS feeds, scores them against the user's profile (rules built from their CV in an onboarding wizard; there are no built-in rules), and shows a report page with tabs «Подавайся / Можливо / Збережені / Подав / Сховані» (Apply / Maybe / Saved / Applied / Hidden). It can also push relevant new jobs to a Telegram bot. The interface is in Ukrainian and English (`src/i18n/`, see below). Code, comments and the README are in English.

## Commands

```
npm i
npm run build      # esbuild → dist/ (copies public/ and the pdf.js worker, bundles background/report/options/onboarding/popup)
npm run typecheck  # tsc, noEmit; covers src/ and test/
npm test           # tsx --test test/*.test.ts (node:test)
npm run release    # typecheck + test, bump patch in public/manifest.json, build, snapshot dist/ into extensions/job-radar-<version>/
npm run release -- minor   # bump minor instead (also: major)
npm run zip        # zip the release matching the current manifest version (for Chrome Web Store)
npm run prettierfix    # format everything
npm run prettiercheck  # check formatting
```

Code style comes from Prettier (`.prettierrc`, same as the ICC play-area project): 4-space indent, single quotes, no semicolons, trailing commas, print width 120. Run `npm run prettierfix` after editing.

Tests use Node's built-in `node:test` and `node:assert/strict`, run through tsx, one file per area: `feed` (RSS, normalize, merge/dedup, prune, freshness, job pages, Telegram), `scoring`, `profile` (buildRules, formats, city, AI tools, upgradeRules), `cv` (splitCv, analyzeCv, the tech dictionary), `language`, `salary`, `feeds` (search URL → RSS, suggestions), `pageJob` (the popup's page parsing) and `backup`. Shared fixtures live in `test/fixtures.ts`: `RULES` and `SOURCES` (the former built-in rules and feeds), `SETTINGS`, inline RSS strings for Djinni and DOU, a plain-text `CV` and `NOW`. One file: `npx tsx --test test/salary.test.ts`; one test by name: `npx tsx --test --test-name-pattern="Android" test/*.test.ts`. A failing test makes `npm test` (and so `npm run release`) exit non-zero.

To load the extension: `chrome://extensions` → Developer mode → "Load unpacked" → select `dist/` (dev) or a folder in `extensions/` (test builds). `public/manifest.json` has a `key` (a public key, no private key is kept), so every unpacked build gets the same ID, `ncincnjejoopponbjalpajmpmibdmhel`: loading a newer `extensions/` folder keeps the storage and runs the update path instead of starting over. `npm run zip` strips `key`, since the Web Store assigns its own ID. `public/manifest.json` is also the only place the version lives (`package.json`'s version isn't used). `release.mjs` bumps the patch on every run (or `minor`/`major` when passed as an argument) and rolls it back if the build fails. `extensions/` is gitignored and created on demand. Old builds are kept until you delete them.

## Architecture

**Layout:** `src/core/` is pure logic with no `chrome.*` (types, defaults, rss, normalize, scoring, collect, jobPage, pageJob, techs, cv, profile, salary, language, feeds, backup). `src/services/` holds integrations (`storage.ts` for `chrome.storage`, `telegram.ts` for the Bot API, `pdf.ts` for pdf.js). `src/pages/` holds the UI, written in Preact (no UI framework, styling is plain `public/styles.css` with class names). `report.tsx`, `options.tsx`, `onboarding.tsx` and `popup.tsx` are the entry points that mount into `<div id="app">`, and shared parts live in `components/`, `hooks/` and `utils.ts`. JSX is configured through `jsxImportSource: "preact"` in tsconfig, and esbuild picks that up. Import hooks from `preact/hooks`, not `react`. `src/background.ts` is the service worker. `src/i18n/` holds the interface texts. Keep anything that touches `chrome.*` out of `core/` and `i18n/`.

**Build:** `build.mjs` bundles five entry points (`background`, `pages/report`, `pages/options`, `pages/onboarding`, `pages/popup`) as ESM targeting chrome116 into `dist/`. It uses the esbuild object form for `entryPoints`, so the output stays flat (`background.js`, `report.js`, …) and matches what `manifest.json` and the HTML files reference. The static files from `public/` are copied in as is. The runtime dependencies are `preact` and `pdfjs-dist`, both bundled. pdf.js is only imported by the onboarding page, which comes out at about 900 KB. Its worker `pdf.worker.min.mjs` is copied into `dist/` and loaded through `chrome.runtime.getURL`. MV3 forbids remote code, so everything must be bundled locally. pdf.js 6 no longer uses eval, and in v6 `destroy()` lives on the loading task, not the document.

**Pure core vs. chrome glue:** The data pipeline in `core/` stays free of `chrome.*` so it can be tested under Node:

-   `rss.ts` is a regex-based RSS parser. It deliberately avoids `DOMParser`, which doesn't exist in the MV3 service worker. It handles CDATA, entity-escaped HTML (DOU), and `dc:creator`. The real Djinni feed has no `dc:creator` or any other company field, so Djinni jobs start with an empty `company`. The service worker fills it in later from the job page (see below). The fixture in `test/fixtures.ts` includes `dc:creator`, so it doesn't match the live feed.
-   `jobPage.ts` reads `hiringOrganization.name` from a page's schema.org `JobPosting` JSON-LD. Djinni job pages include it, and their `datePosted` equals the RSS `pubDate`.
-   `normalize.ts` turns a `RawItem` into a job. It splits DOU titles of the form `"Role в Company, location"`, strips tracking params to get a canonical URL (used as the job `id`), and builds a `dedupeKey(title, company)` for cross-source dedup. The key is only used when `company` isn't empty. Djinni companies are filled in after the merge, so `refresh()` runs `mergeDuplicates` after the page checks to join copies that now share a key.
-   `scoring.ts` starts from a base of 20 and adds the weights of matching regex rules, clamped to 0–100. Rules can be `titleOnly`, and can have an `unless` regex that cancels the rule when it matches title + description (for example, the wizard's full-stack penalty is skipped when the text mentions an allowed tech such as .NET). Invalid user regexes are skipped silently while scoring, and the options page rejects them on save. Weight-0 rules add nothing and aren't shown as reasons. They exist to mark a tech as "listed". `scoreJob(title, description, rules, options)` takes `ScoreOptions` (`collect.ts` passes the whole settings object). Its `techBonusCap` (default 30) caps the sum of positive weights from tech rules (rules that target a dictionary tech) by adding a «Понад ліміт за технології» reason, so a junior job matching the whole stack can't reach 100. Rule-vs-dictionary analysis is cached per rules array in a WeakMap, and compiled patterns in a Map. `ScoreResult.neutral` (stored as `Job.neutral`) lists the dictionary techs a job mentions that no reason accounts for: weight-0 rules, and techs outside the unlisted penalty (DevOps tooling, the user's own categories). The report shows them as plain chips. An update makes `background.ts` rescore all stored jobs, so new fields like this fill in. With `unlistedTech` passed, dictionary techs that no rule targets are penalized as another stack. A rule targets a tech through the same pattern, the same label, a pattern matching the tech name (non-`titleOnly` rules only, since broad title rules like `NO_LEVEL_IN_TITLE` match any name), or an `unless` naming it. Each such tech in the title gets `unlistedTech.title` (−15). In the description, `unlistedTech.description` (−8) applies per tech, up to 5, and only for frontend/backend/mobile techs whose category has no positively weighted tech (the user's "own" categories). With no rules at all (before the wizard) these penalties are skipped too, so every job stays at the base score, and the report shows a notice linking to the wizard (likewise when no source is enabled). Tests mostly call `scoreJob` without options, so the cap and these penalties are off there. They score against `RULES`, a fixed Senior Frontend React/TS rule set in `test/fixtures.ts` (the former built-in rules). `defaults.ts` has empty `sources` and `rules` arrays (`test/fixtures.ts` has its own `SOURCES` fixture, the former defaults). Changing defaults doesn't affect users who already saved settings. The same goes for rules generated by `buildRules`: when a generated pattern is fixed, add the old → new pair to `PATTERN_FIXES` in `profile.ts`. On an extension update `background.ts` runs `upgradeRules` on the saved rules (only patterns it generated, matched exactly, so user-edited ones stay) and rescores the stored jobs. Office words are matched as whole words (`OFFICE_WORD`), because "Chief Operating Officer" and "back-office systems" used to count as an office.
-   `techs.ts` is the technology dictionary: id, name, category and a case-insensitive regex. The same regex finds the tech in a CV and becomes the scoring rule pattern, so it must avoid false positives (Java vs JavaScript, React vs React Native, `.NET` vs `example.net`). When the rule pattern is too narrow for CVs, an optional case-sensitive `cvPattern` is used there instead. Go is the example: in jobs it matches only Golang, "Go developer", "(Go)" and "Java/Go", but in a CV a capitalized `Go` is the language. Android goes the other way: its `cvPattern` is stricter, since a frontend CV saying "shipped it into our iOS and Android apps" or "tested on Android devices" names a platform, not Android development ("built Android apps" and a skills list still count). There are tests for these.
-   `cv.ts` has `splitCv`, which cuts CV text into blocks at date ranges (`Mar 2022 – Present`, `03.2019 - 02.2022`, `2016 — 2019`, en/uk/ru month names, "present"-like words) and at section headings, which start undated blocks. A heading is matched loosely: a short line with no digits and no text after a colon, containing a keyword such as skills, education, languages or certification, so "CORE SKILLS", "EDUCATION AND CERTIFICATION" and "Технічні навички" all count, while "Stack: React, …" inside a job doesn't. It uses Unicode `\p{L}` boundaries, because `\b` doesn't work with Cyrillic. Month-only ranges like "May – Dec 2018" aren't recognized and stay inside the surrounding block. A dated block that mentions some tech counts as a job, and education ranges don't. `analyzeCv` sets relevance to 60% recency plus 40% frequency. Recency is by job position (latest 1, previous (n−1)/n, …), not by years, so a long current job doesn't age the previous one. Frequency is the share of jobs that mention the tech. A tech that only appears in a skills list gets recency 0.4 and frequency 0. Without any dates, the score falls back to the mention count. `suggestWeight` is relevance/5, which gives 1–20. `experienceYears` preselects the level.
-   `profile.ts` has `buildRules(profile)`, which turns the wizard answers into `Rule[]`. It covers tech weights, unwanted techs (−12), a direction title bonus, a level matrix (own level +12, lower levels penalized: for a senior, middle −25 and junior −40), "no level in the title" scored as middle (`NO_LEVEL_IN_TITLE`, a negative-lookahead title-only pattern; for a senior it has `unless: SENIOR_YEARS`, which matches "5+ years" and similar), Team Lead, Tech Lead and Staff/Principal (each +8 if wanted, −10 if not), languages (`languageRules`), AI coding tools (+10 only if wanted, no rule otherwise; `AI_TOOLS_PATTERN` matches using tools such as Claude Code, Cursor, "AI-first" or "AI-assisted development", not building AI products, which is the LLM/AI tech, and it targets no tech, so it stays outside the tech cap), formats (each one always yields a rule so the choice is visible: remote +15 or −10; hybrid +5 or −8; office +5 or "only office" −25; with a city, the hybrid and office bonuses (labels «Гібрид: Одеса», «Офіс: Одеса») need the city in the text too, via an `inCity` lookahead pattern, so a Kyiv office is no plus for someone in Odesa, and `upgradeRules` ties older saved bonuses to the city of the saved «Місто: …» rule; relocation +5, or −25 for a required move when not chosen) "office/hybrid elsewhere" (−20 for office or hybrid wording unless the text mentions remote or the user's city; without office/hybrid chosen it's "office/hybrid without remote") and a city (`cityPattern` drops the last letter to catch Ukrainian inflections), company type, and full stack (−30, optionally with `unless` built from the allowed techs' patterns).
-   `language.ts` has the spoken languages (English, Ukrainian, German, Polish, French, Spanish) and CEFR levels 1–6 with level words in en/uk/ru ("upper-intermediate", "вище середнього", "B2", "fluent"…). `languageRules(skills)` makes, per language the user speaks below C2, a −20 rule for a level word above theirs in the same clause as the language name (either order, up to 25 chars without `.,;`), with `unless` for their level or lower, so "B2–C1" doesn't hit a B2 speaker. English without a level gets "не володієш" (any stated level counts). Other unspoken languages share one rule that also counts "required/speaking/skills". Rules compile with the `i` flag only, so the patterns spell out Cyrillic tails (`[а-яіїєґ]*`) instead of `\p{L}` and avoid `\b` next to Cyrillic. `cvLanguages(text)` reads the highest stated level per language from a CV, where "native"/"рідна" also means C2 (too loose for job texts: "React Native"). The wizard adds no languages beyond the CV's: with an empty list, any stated requirement for any language counts against a job.
-   `salary.ts` has `findSalary(title, description)`, which returns `{min?, max?, currency, period}` or null. It needs a currency mark ($, €, грн, USD…) and only trusts a bare amount in a known spot: the title, the very start of the description (Djinni prepends the salary there), or the first `Локація:` line (where `normalize` puts the DOU title's location part, which holds the salary). Elsewhere it needs a period (`/hour`) or a word like salary/rate/зарплата just before, so a "$1000 bonus" isn't taken for pay. `mergeFeed` stores it on `Job.salary`, and `rescoreAll` re-reads it. `belowMinSalary` compares only a known upper bound with `Settings.minSalary` ($/month; hourly ×160, rough fixed EUR/UAH rates), so jobs without a salary or with only "from X" are kept.
-   `feeds.ts` knows the sites' search filters. A feed is the site's search page as RSS with the same query (`djinni.co/jobs/?…` → `/jobs/rss/?…`, `jobs.dou.ua/vacancies/?…` → `/vacancies/feeds/?…`), and `toFeedUrl` does that conversion (dropping `page`). Djinni filters by its own category keys in `primary_keyword` (`DJINNI_KEYWORDS`, taken from the category tree on djinni.co/jobs/), case-sensitive. An unknown value is silently ignored and the feed returns the latest 100 jobs from every category (`primary_keyword=React` is ignored, `React.js` works), so `unknownDjinniKeywords` flags it. A feed also returns 100 when the filter is real and broad (`ML AI`), so the count can't tell. DOU filters by `category` (`DOU_CATEGORIES`, from the select on jobs.dou.ua/vacancies/) or `search`. `TECH_FEEDS` maps tech ids to both, and `suggestFeeds(techIds, direction)` builds the wizard's list in weight order, up to 5 per site with the first 2 ticked. `toSources` keeps the id of a feed that's already a source. Check new keys against the live feed (politely: a couple of requests with pauses, no cookies).
-   `collect.ts` holds `mergeFeed` (dedup by id, then by dedupeKey; appends to `sourceIds` on a match and keeps another site's URL in `Job.alternates`), `mergeDuplicates` (joins copies from different sites that share a key once the Djinni company is known: the first seen copy stays and takes the others' sources, URLs and furthest status; two postings on one site are never merged; merged-away jobs are left out of that run's notifications), `rescoreAll` (keeps user statuses), and `prune(jobs, sources)` (drops jobs older than 45 days, and jobs none of whose `sourceIds` is still a source, unless they are `saved` or `applied`; disabled sources count as present). The worker prunes on refresh, on `settings-changed` and after an update, so removing a source on the options page takes its jobs with it (the wizard replaces the sources and drops the jobs outright, see Onboarding).

**Service worker (`background.ts`):** This is the only place that fetches and orchestrates. It schedules a `chrome.alarms` alarm from `intervalHours` (`schedule()` keeps an alarm whose period is unchanged, so saving the settings doesn't push the next run back; a new one is timed from `lastRun`). Chrome stops an idle worker after 30 seconds, and pending fetches and timers don't count, so `refreshOnce()` pings `chrome.runtime.getPlatformInfo` every 20s while a refresh runs (without it, a refresh with page checks was killed before saving anything); every fetch has a 30s timeout. `refresh()` fetches the enabled sources (at most `MAX_SOURCES` = 10; the options page and the wizard refuse to save more, and the interval is at least `MIN_INTERVAL_HOURS` = 2, both in `defaults.ts`, since every request comes from the user's IP) one after another with a 1.5s pause between them and merges them. Next, `checkJobPages()` fetches job pages from sources with `fetchPages` on (shown as «перевіряти сторінку» on the options page; the wizard and pasted links turn it on for Djinni feeds) to read details the RSS lacks. For now that is only the company, so `needsPageCheck` only picks jobs with an empty `company`. If more fields are added to `parseJobPosting`, extend that condition too. It handles at most 20 per run, newest first, 0.7s apart, and only fresh jobs (`needsPageCheck`). `pageChecked` makes sure each page is fetched only once, and a failed fetch is retried on the next run. Finally `refresh()` prunes, saves, updates the badge (count of `new` jobs that pass `isRelevant`), sends to Telegram and fires a notification. `refreshOnce()` makes sure only one refresh runs at a time. Only the worker writes `jobs`, and `writeJobs(fn)` queues every read-modify-write so they never interleave. A refresh works on its own copy for a minute or so, so its final write, inside `writeJobs`, first applies `statusesDuringRefresh` (statuses set meanwhile, which `set-status` also saves right away) and re-reads the settings to prune and rescore with the latest rules and sources; the map is cleared when a refresh starts, so an entry left over from its last moments can't override a later change. Pages never save `jobs` themselves: a whole-map write from the report used to be undone by a running refresh (statuses went back to «new»).

**Messaging:** The pages talk to the worker through `chrome.runtime.sendMessage` with these `type` values: `refresh`, `settings-changed` (prune, rescore all jobs, reschedule, update badge; with `reset: true`, sent by the wizard, it first waits for a running refresh and drops every job except saved and applied ones), `telegram-test`, `set-status` (`{ids, status}` from the report, one card or «Позначити переглянутими»; saves now and updates the badge) `add-job` (a job from the popup, which a running refresh doesn't know, so it waits for that refresh, then `addPageJob`) and `import` (a backup file from the options page: «Резервна копія» on the General tab saves `makeBackup` from `core/backup.ts`, the settings plus saved and applied jobs, as JSON; restoring checks the file with `readBackup`, which fills settings fields the file lacks from the defaults, and the worker waits for a running refresh, saves the settings with `upgradeRules` applied, adds the jobs with `importJobs` (applied wins over saved), prunes and rescores; the page then reloads). When you add a setting that affects scoring or scheduling, make sure the options page sends `settings-changed`.

**Storage (`storage.ts`):** `chrome.storage.local` holds three keys: `settings` (shallow-merged over `DEFAULT_SETTINGS`, so new top-level fields get defaults but nested arrays don't), `jobs` (`Record<id, Job>`), and `lastRun` (per-source results and errors). Pages read storage through `useStorage(loader)` (`pages/hooks/useStorage.ts`), which reloads on every `chrome.storage.onChanged`. The report doesn't keep its own copy of jobs. It sends `set-status` and re-renders from the change event. The options page reads settings once into a local draft so edits aren't clobbered.

**Thresholds:** `applyThreshold` decides between «Подавайся» and «Можливо». Jobs scoring below `hideBelow` go to «Сховані». `maxAgeDays` (default 3, capped at `MAX_AGE_DAYS` = 45, the prune horizon) marks jobs as stale based on `publishedAt`, falling back to `firstSeen`. Stale jobs also go to «Сховані». This is a view-time filter, so raising the setting brings older stored jobs back. `minSalary` (0 = off, set on the options page or in the wizard) hides jobs whose salary's upper bound is lower, the same way. `isOpenToApply()` in `collect.ts` combines the age and salary checks, and the report uses it. `isRelevant()` (open to apply and score ≥ `applyThreshold`) is the single rule for the badge, notification and Telegram, so use it rather than re-checking the score. Saved and applied jobs ignore score and age.

**Report page:** tabs by status and score, a text search, and a «Усі / Djinni / DOU» switch (`PLATFORMS` and `platformsOf` in `pages/utils.ts`, by the job's source feed hosts and its own URL, so a job deduped across both sites shows under each, with «Djinni / DOU» in its meta line). Clicking the title of a job with `alternates` opens `LinkChooser`, a native `<dialog>` asking which site to open (Ctrl/Cmd-click opens the first URL directly). The switch narrows the tab counts too and is remembered in `localStorage`. Jobs saved from the popup (LinkedIn, Work.ua…) have no source: they show only under «Усі», labelled with their site (`platformLabel`, `SITE_LABELS`).

**Options page:** The page has three tabs: «Загальні» (`general`: thresholds, interval, notifications, Telegram), «Джерела» (`sources`) and «Фільтри» (`filters`, the scoring rules). The open tab is kept in `location.hash`. All tabs share one draft and a single Save button. A validation error carries `tab`, and saving switches to that tab. Sources and rules are edited row by row in `components/SourcesEditor.tsx` and `components/RulesEditor.tsx`. Rows carry a local `key` for rendering, and rule weights stay strings until save. `fromDraft()` validates every row and refuses to save with a message naming the row (empty fields, bad regex in `pattern`/`unless`, bad URL or a host outside `ALLOWED_HOSTS`). New sources get a generated `src-…` id. A source URL that's a site search page is converted to its feed on change (filling an empty name and `fetchPages` for Djinni) and again in `fromDraft`; an unknown Djinni key shows a non-blocking warning. Existing ids must never change, because `Job.sourceIds` refers to them.

**Onboarding (`pages/onboarding.tsx`):** `background.ts` opens it on `onInstalled` with reason `install`, and the «Фільтри» tab links to it. It has four steps: `UploadStep` (PDF only, rejects scans with no text layer; or «Без CV — налаштувати вручну», which runs the same steps with an empty stack), `TechsStep` (`TechRow`s with an editable weight and an include checkbox: found in the CV with relevance, or added by hand; dictionary chips cycle through want → avoid −12 → neutral, where want adds a row weighted `ADDED_WEIGHT` (+5 with a CV, +12 without, since then it is the stack)) `PrefsStep` and `SourcesStep`. Preferences are guessed when leaving the techs step: direction from the stack's weights, level from the CV's years (middle without a CV), the salary from the current settings. The sources step lists `suggestFeeds` for the positively weighted stack, never the current sources: re-running the wizard (a backend CV after a frontend one) is a fresh start. The suggestions are grouped by site (`PLATFORMS`): ticking Djinni or DOU in «Де шукати» opens its feeds, and only ticked sites' feeds are saved (`chosenFeeds`). Pasted feeds go to a separate «Свої джерела» block (`FeedRow.custom`) and are saved whichever sites are ticked. A pasted site search URL is converted, checked with one cookie-less fetch for the job count (skipped when the Djinni key is unknown, which adds it unticked with a warning). Finishing replaces `settings.rules` with `buildRules(...)` and `settings.sources` with the ticked feeds (`toSources`; Djinni ones get `fetchPages`), sends `settings-changed` with `reset: true` and `refresh` (not awaited) and redirects to `options.html#filters`. The page scrolls to the top on every step change. The CV text is never stored.

**Popup (`pages/popup.tsx`, the toolbar action; the report opens from it):** on open it injects `snapshotPage` into the active tab (`chrome.scripting.executeScript`, allowed by `activeTab`). That function is serialized, so it must use nothing outside its own body. It returns a plain `PageSnapshot` (URL, tab title, JSON-LD blocks, what the site's selectors found: title, company, top lines, salary, description; h1, selection, main text), and `core/pageJob.ts` `jobFromPage` turns it into a job. The description comes from the selection (at least `MIN_SELECTION` chars), the site's selectors, or the JSON-LD JobPosting (HTML stripped, `TELECOMMUTE` as "Remote"), in that order; the salary (the selectors' one, or `baseSalary`) goes first, as a line `findSalary` trusts, then the top lines. Otherwise the whole page text is scored with `guessed: true` and a warning. The URL is canonical: no query, and LinkedIn's `?currentJobId=` or `/jobs/view/slug-123` become `/jobs/view/123`, so saving a Djinni page matches its feed job. `pageToJob` scores it like a feed job but with no `sourceIds`, so `prune` keeps it only as saved or applied, which are the only two buttons. `selectorsFor(url)` picks a site's `SiteSelectors`: LinkedIn (`SITE_SELECTORS`), DOU (`DOU_SELECTORS`: `h1.g-h2`, `.b-compinfo .l-n a`, `.sh-info .place` / `.salary`, `.vacancy-section`, checked in its HTML; DOU job pages have no JobPosting JSON-LD, and their whole text includes a «Схожі вакансії» column) and Work.ua (`WORK_UA_SELECTORS`, read through the accessibility tree only, since curl gets the Cloudflare challenge: the «Про вакансію» heading climbs to the whole job card, which holds the title too, so the company (`/jobs/by-company/` link) and the salary (an element whose whole text matches `SALARY_TEXT`, e.g. «Від 1200$») are looked for inside that card) and Robota.ua (`ROBOTA_UA_SELECTORS`, also through the accessibility tree: its only `<article>` wraps the whole page with the side lists, and the text has no heading, so with no description selector or heading the description is the job card: from the h1 up to the first block holding a `cardCompany` link (in the live DOM, a 102-char header), then past wrappers with the same text, then while a parent at least doubles it (`lib-content`, 5000+ chars), stopping before the wrappers that add the hot list; this fallback is skipped for sites with a `descriptionHeading`, where a missed description should fall back to the page text with a warning). Other sites get none. The signed-in LinkedIn UI (checked in 2026 through its accessibility tree, Ukrainian UI, `/jobs/collections/recommended/?currentJobId=…`) has generated class names, so it's found by structure: the title is a heading linking to `/jobs/view/`, the description the `<article>` around the «About the job» / «Про цю вакансію» heading (`descriptionHeading`), and the top card (location line, On-site/Remote/Hybrid button, company link) is the largest block around the title that doesn't contain the description. Taking the company from inside the card matters: an earlier «Про компанію» section has `/company/` links too («Показати більше»). The newer search (`/jobs/search-results/?currentJobId=…`) has no `<article>` and no title element: there the heading «Про цю вакансію» sits in wrappers of its own (the accessibility tree hides them), so the description is the first ancestor with 100+ chars more text than the heading; title and company come from the tab title (`linkedinTitle`, «Role | Company | LinkedIn»), and the workplace type from an element in the job pane (outside the description) whose whole text is «Remote»/«Hybrid»/«On-site» (`workplace`). The old class names stay first for the signed-out page.

**Languages (`src/i18n/`):** `uk.ts` is the Ukrainian dictionary and defines `Messages`; `en.ts` must match it (TypeScript checks every key). Messages are strings or functions of what varies; a sentence with a link or a chip in it is a function that gets wrappers (`(s) => <a …>{s}</a>`) and returns children, so it stays one message. `t` is a live binding to the current dictionary, set by `setLocale`; `resolveLocale(settings.locale, navigator.language)` maps `'auto'` to Ukrainian for a uk/ru browser and English otherwise. Every page calls `applyLocale(settings)` (`pages/utils.ts`) while rendering, before using `t`, and sets `document.title`; the options page reloads after a save that changes the language. The worker sets it from the settings before a refresh, a rescore and the Telegram test, so notifications, Telegram messages, run errors and score reasons follow it. Core uses `t` too, for the texts it makes: score reasons (`t.score`), feed names (`t.feeds`), `formatSalary` (`t.salary`). Generated rules carry `Rule.labelKey` (`{id, args}`, `labelled(id, …args)` in `buildRules`/`languageRules`), and `ruleLabel(rule)` renders it in the current language, `label` being the text at creation; the options page keeps the key on save only while the label is unchanged, so a renamed rule keeps its name. `upgradeRules` gives older saved rules their key by matching the Ukrainian labels they were generated with (`LEGACY_LABELS`, language names). Saving the settings rescores every job, so stored reasons are made again in the new language. The popup stores a problem as a message key, not text, since it reads the tab before the settings load. The manifest's name, description and action title come from `public/_locales` (`default_locale: en`). Regexes that read job texts (Ukrainian words in `profile.ts`, `salary.ts`, `cv.ts`, `pageJob.ts`…) aren't interface text and stay as they are. `test/i18n.test.ts` checks the English dictionary has no Cyrillic left and the same number of texts as the Ukrainian one.

**Permissions:** The host permissions in `public/manifest.json` cover only `djinni.co`, `jobs.dou.ua`, and `api.telegram.org`. `activeTab` + `scripting` are for the popup only: no host permission for LinkedIn and others, no content scripts. LinkedIn forbids automated collection, and Work.ua and Robota.ua (pages and their APIs, `api.robota.ua`, `dracula.robota.ua`) sit behind a Cloudflare JS challenge, so they're never fetched; the user rates their jobs from the popup. Adding a new source domain means updating the manifest and `ALLOWED_HOSTS` in `SourcesEditor.tsx`, and `PRIVACY.md` (the Web Store privacy policy, which lists every address the extension sends requests to and why each permission is needed). Keep it in step with any new request or permission.
